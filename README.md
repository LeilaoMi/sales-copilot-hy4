# 销冠助手 · 个人销售作战台

一个**给一线销售自己用**的轻量级工作台：客户、商机、跟进、话术、业绩目标、AI 助手全在一个页面里，双击就能打开，不需要安装、不需要公司的 CRM 账号。电脑上拖拽看板，手机上点按操作，都能离线使用。

> 设计原则：**不为汇报服务，只为签单服务。** 打开后 3 秒能回答三个问题——今天该打给谁？这个月还差多少？下个月大概能回多少？

## 八个模块

### 1. 战情台（首页）
- **每日晨报**（第一屏）：打开就看到三件事——今天有几件事、最紧急的是哪件、这个月还行不行。下方卡片是详情，这里不重复铺开
- **一句话录入**：打开就能说，回车自动拆字段。详见下方专节
- **目标环形进度**：本月回款 / 月度目标，自动算出还差多少、本月剩几天
- **今日作战清单**：按逾期天数排序，"今天该打给谁"不用再想；点「记跟进」一键顺延下次联系日期
- **加权预测**：各阶段商机金额 × 阶段赢率，比拍脑袋准
- **核心指标**：赢单率、客单价、平均成交周期、本季累计
- **近 6 月业绩折线**、**销售漏斗**、**客户分级分布**
- **冲刺提示**：本月回款的**保守 / 乐观区间** + 目标倒推判断，详见下方专节

### 2. 客户库
A/B/C 分级 + 行业/来源/状态标签、下次跟进日期（逾期标红、今天标黄）、在谈金额与已成交金额自动汇总、搜索筛选排序、导出 CSV、360° 详情弹窗。**手机上每个客户卡片都有「打电话」「复制微信号」按钮**，客户电话来了不用翻通讯录。

### 3. 商机看板
- **电脑端**：7 列 Kanban，拖动卡片改阶段
- **手机端**：列表化展示，点选阶段下拉即可推进，**原生 HTML5 拖拽在触屏上不可用，所以干脆不做拖拽**，单手就能操作
- 拖到/选到「赢单」：自动写入成交日期、客户状态转「已成交」、清除跟进提醒
- 拖到/选到「输单」：提示补录输单原因（三个月后回看输单原因，能找到真正的短板）

### 4. 跟进日志
按客户/方式筛选的倒序时间线；左侧常驻「待跟进」清单。记一笔跟进时可同时设定"顺延下次联系到哪天"，避免所有客户都躺在列表里过期。

### 5. 话术库
内置 **46 条**实战话术，按场景分八类：异议处理 16、催单推进 6、开场破冰 5、需求挖掘 5、售后维护 5、谈判博弈 4、方案报价 3、复盘沉淀 2。点「复制」直接粘到微信。支持自建分类与内容——把客户最让你卡壳的那句话记下来，写出你的答案。

**检索是本地的四路加权，不是关键词过滤**（借鉴了向量检索的思路，但不需要任何 AI 和向量库）：

| 权重 | 信号 | 解决什么问题 |
|---|---|---|
| 0.40 | 意图匹配 | 你说「客户嫌贵」，能命中「太贵了」那一条，哪怕字面上一个词都不重合 |
| 0.30 | IDF 加权 bigram 余弦 | 「价格」这种满库都有的词权重低，「回扣」这种稀有的词权重高 |
| 0.15 | 全文 / 标题命中 | 精确输入时给精确结果 |
| 0.15 | 标签字面命中 | 你自己打的关键词也算数 |

四路加起来排序，比 `indexOf` 聪明，又比接一个向量库轻——**断网、无 Key、双击打开都能用**。

### 6. 周报
把「这周干了什么」自动归拢成一页，**纯本地计算，不调用 AI，断网可用**。

- **六个时间范围**：本周 / 上周 / 近 7 天 / 本月 / 上月 / 近 30 天
- **数字卡片**：新增客户、跟进次数、推进的商机、赢单数、赢单金额、沉淀话术。**为 0 的项不显示**——周报里出现「成交 0 单」是自曝其短，还挤占了真正有信息的数字的位置
- **重点客户**：按在谈金额降序，附客户原话
- **接下来 7 天**：只列有明确日期的承诺
- **风险提醒**：冷住 21 天的单子、丢的单、该跟没跟的客户、月底目标缺口（**只剩 ≤10 天才喊**，月初喊「还差 80%」只会让人麻木）
- **文字版 + 一键复制**：分「进展 / 重点客户 / 下一步 / 风险」四段，改几个字就能直接发给领导

为什么不让 AI 写：销售写周报真正的痛苦不是不会写，是**想不起来这周干了什么**。周报八成的价值是把散落一周的动作自动归拢——这件事本地手里就有全部数据，而且要的是**确定**：AI 会漏掉一条跟进，本地算术不会漏。AI 只用来做最后一步润色（「AI 润色」按钮，提示词严格要求不得改动任何数字）。

> 「本周」从**周一**起算。周日报周报少算周六周日，是要挨骂的。

### 7. AI 助手（可选增强）
在「设置」里配置自己的 OpenAI 兼容 API（DeepSeek / 通义 / OpenAI 等，**Key 只存本机，直连服务商**）后可用：
- **写跟进话术**：根据客户画像 + 最近跟进 + 当前阶段，生成可直接发的微信/电话话术
- **本周周报**：汇总本周新增客户、跟进、赢单、下周重点，直接粘贴给老板
- **输单复盘**：分析所有输单原因，给出 TOP3 原因 + 3 条改进动作
- **客户作战建议**：为某个重点客户输出决策链、卡点、下一步动作、风险提醒

**没配 API 也能用**：点击「复制提示词」，粘到你自己的 AI 工具里生成。

### 8. 设置
姓名、月度目标、提成比例；**云同步**（自建 / Supabase / EdgeOne，含连接状态与手动同步）；数据码跨设备迁移、JSON 备份/恢复、CSV 导出、AI 配置、PWA 安装提示、载入示例/清空数据。

顶栏右侧有个**同步状态胶囊**：灰色=未启用、绿色=已同步、蓝色闪烁=同步中、红色=连接异常。点它可立即同步一次。

### 附 1：聊天记录情报提取（客户详情里）

客户详情页和商机详情页都有「整理聊天记录」按钮。把和客户的微信/电话记录整段粘进去，本地规则引擎拆成四桶：

| 桶 | 内容 |
|---|---|
| 客户顾虑 | 他担心什么 |
| 承诺事项 | 他答应了什么、什么时候 |
| 决策信息 | 谁拍板、预算多少、什么时候要 |
| 下一步 | 我要做什么、什么时候做 |

**勾选后一键写入跟进记录**，不用自己再誊一遍。不勾选就不写，不给脏数据。

这个功能的价值在于：销售和客户的对话是有信息量的，但聊天记录躺在微信里，CRM 里只剩下「2026-08-29 电话沟通」这种废话。**把原文变成结构化情报，才是以后能复盘、能让 AI 分析的前提**。

### 附 2：战后沉淀（赢单 / 输单时自动触发）

把商机拖到「赢单」或「输单」，会弹出一个框，从这条商机的跟进历史里**自动挑出候选话术**，你勾几句就存进话术库。

- **带引号的原话优先**——客户自己说的话才值得记，销售自己做了什么那是流水账
- **赢单和输单分开存**：赢单的经验是照着再做一遍，输单的经验是下次别这么干
- 长句里如果混着别的短句，**留短的那句**
- **同单不重复弹**，**没料不打扰**——翻不出有价值的话就不弹框，不骚扰

三个入口都接上了：看板下拉、拖拽、健康度一键推进。

> 这里曾经有个**藏了很久的 bug**：提取函数读的是 `x.note`，而数据库里字段叫 `content`。于是 `notes` 恒为空数组，这个函数三年如一日地返回 `null`——**战后沉淀从来没生效过**，而因为没有报错，谁也没发现。字段对不上是最难查的一类 bug。

### 附 3：此刻该说什么（客户详情页顶部）

话术库做得再聪明，也是**等人来搜**的。可销售真正被问住的那一刻，他在微信对话框里、在电话上，根本不会切到这个网页去搜——于是 46 条话术就成了一本没人翻的字典。

换个思路：**销售什么时候一定会打开这个工具？** 客户来电话前、打完电话后、准备联系一个客户之前，他都会点开客户详情。那就把话术**推到他眼前**。

打开任意客户详情，顶部就是这个客户此刻该说的三句话：

| 场景 | 给什么 | 判定依据 |
|---|---|---|
| **从没联系过** | 开场破冰 | 零跟进记录 |
| **冷了太久** | 重新激活话术 | 超过 21 天没联系（和周报同一个口径） |
| **最近有明确顾虑** | 针对那个顾虑的应对话术 | 从最近 3 条跟进里识别意图 |
| **跟进写得太简略** | 按当前阶段给 | 「沟通顺利」这种空记录挖不出东西，按商机阶段兜底 |

几条刻意的克制：

- **最多三条**。销售点开详情是想确认这人是谁，不是来读文章的。给十条等于一条都不给。
- **默认收起全文**，点标题才展开。三条都铺开会把下面的商机和时间线挤没。
- **每条都带「为什么给你这条」**（如「命中场景：价格异议 / 竞品对比」）。工具必须能解释自己，否则销售看两次就不信了。
- **只认最近 3 条跟进**。一个月前的异议早不算数了，拿它推荐话术会驴唇不对马嘴。
- **用户自己攒的话术标「你记的」**——那是真踩过的坑，和内置的分量不一样。

> 走查时发现话术库有个真空洞：**「什么时候能交货」一条都没有**。这是客户问得极多的一句话，而且是**推进信号**（他在认真算自己什么时候能用上），比「再考虑考虑」值钱得多。已补上 delivery 意图槽 + 2 条交付话术，老用户升级时会自动补进库里。

### 附 4：标签页待办徽章

**这是整个工具唯一「主动」的地方。**

先说清楚做不到什么：纯前端、无服务器的网页，**没法**在页面没打开时弹窗提醒，浏览器不允许。硬做推送是做不到的，别自欺欺人。

但销售很可能把这个页面**一直开着**——当成工作面板之一，旁边是邮箱、Excel、客户微信群。这时候浏览器标签栏上那个「(3)」就是唯一还在持续提醒他的东西：不弹窗、不打断、不吵，但他干活时眼角余光一直能看到还有几件事没办。

- 标题变成 `(3) 销冠助手 · 个人销售作战台`
- 图标换成**蓝底白字的数字**（不画「销」字是刻意的：canvas 里的中文字体不可控，系统没装中文字体就画成一坨豆腐块，而阿拉伯数字到哪都有——**拿可靠性换美观**，favicon 只有 16×16，认得清数字就够了）
- 数量归零时标题和图标**都还原**，不会一去不回
- 数字取自「今天到期 + 已逾期」，和首页待跟进清单**同源**——两处算法一旦不一致，用户会发现「标题说 3 件、点进去 5 件」，然后就再也不信这个数字了

## 一句话录入

录入的真正瓶颈**不是打字慢，是流程长**：切页面 → 选客户 → 选类型 → 写内容 → 填日期 → 保存，七步。刚挂完电话站在客户公司楼下，七步就够让人想"等会儿再记"，然后就忘了。

所以战情台最上面常驻一个输入框：一句话说完，回车，自动拆好字段，你看着对就保存。**七步变两步。**

```
输入：拜访了优鲜陈敏，方案过了，下周三再跟进
  ↓
客户    优鲜到家连锁 · 陈敏
方式    拜访
内容    拜访了优鲜陈敏，方案过了，下周三再跟进   ← 保留原文，不硬删关键词
下次    2026-09-02（下周三）
```

### 三条设计原则

1. **规则优先，AI 兜底**。录入发生在电梯口、地铁里、客户公司楼下，**不能依赖网络**。规则能覆盖大部分常见说法，剩下的让用户手动补。
2. **先出结果，再确认**。不做「回车即写库」——误识别会写进脏数据，而脏数据会污染健康度判断和回款预测，**比不记更糟**。
3. **内容保留原文**。用户写的话就是最真实的记录，硬删关键词反而丢信息。

### 拆字段的规则

| 字段 | 怎么认 | 认不出来怎么办 |
|---|---|---|
| **客户** | 全名优先 → 联系人 → 简称（4→2 字逐级缩短） | 有歧义时**列出候选让你选**，不瞎猜 |
| **方式** | 电话/拜访/会议/微信/邮件 关键词 | 留空，弹窗里选 |
| **下次跟进** | 只在**意图词之后**找时间 | 不设，不覆盖原有跟进日 |
| **内容** | 原文照抄 | — |

「下次跟进」这条最讲究：

> 「他说**下周三**报价，**下次周一**再联系」→ 取**周一**，不是周三。
>
> 下周三是对方的时间点，不是我要联系他的日子。找错了就会把跟进日设成一个跟我无关的日子。

另外，**「他说下周三报价」这种没有跟进意图词的不设下次跟进**——那是对方的承诺，不等于我的动作。宁可不设，误设比不设更烦人。

## 本月回款预测 + 目标倒推

### 旧实现有两个硬伤

```js
// 旧代码：注释写着「预计本月内成交」，代码却根本没过滤月份
const likely = sum(openDeals.filter(d => ['quote','negotiate'].includes(d.stage)), d => d.amount);
```

实测后果：**本月只剩 2 天，三单全是 9 月成交，界面却报「本月有望落袋 ¥573,000」**。

这比没有数字更害人——销售会以为这个月能回 57 万，实际上一单都签不下来。第二个硬伤是报价/谈判阶段直接全额相加，等于假设 100% 必成。

### 现在怎么算

| 口径 | 算法 | 含义 |
|---|---|---|
| **保守** | Σ(金额 × 本月内成交概率 × 阶段赢率) | 时间和赢率都打折 |
| **乐观** | Σ(金额 × 本月内成交概率) | 只赌时间，假设谈得成 |

两个口径**恒满足保守 ≤ 乐观**（早期版本把乐观定义成"本月内到期的全额"，月末会出现乐观=0 而保守>0 的倒挂，逻辑上说不通）。

**本月内成交概率**的关键，是看**相对本月还剩几天**而不是绝对天数：

| 情况 | 概率 |
|---|---|
| 预计成交日在本月内 | 100% |
| 已过期但没关掉 | 50%（还有机会，但已经拖了） |
| 比本月多 ≤7 天 | 25%（有可能提前签） |
| 多 8–21 天 | 10% |
| 更远 / 没填日期 | 3% / 15% |

月底剩 2 天时，说"12 天后成交"的单子基本就是下个月的事了；月初剩 28 天时，同样是 12 天后，就在本月内。**早期版本用固定的 15 天窗口，月末会把一堆下月的单算成高概率。**

**阶段赢率**同样从你的成交记录里学：历史上"到达过阶段 X"的已关闭订单中，最终赢单的比例。三条门槛缺一不可——样本 ≥3、**既有赢的也有输的**。只统计到赢单会得出 100%，比默认的 65% 还虚高，宁可不用。

### 目标倒推：这个月还来得及吗

加权预测回答"能回多少"，销售月底真正焦虑的是"**还差多少、来不来得及**"。这是倒推，不是正推：

| 判定 | 条件 | 建议方向 |
|---|---|---|
| **done** | 已达成 | 冲超额提成，或把单子压到下月初 |
| **on-track** | 弹药 ≥ 缺口 | 盯住报价/谈判的单，别最后关头掉链子 |
| **tight** | 弹药 ≥ 缺口 × 60% | 还差多少、剩几天、该补几个单 |
| **unlikely** | 弹药 < 缺口 × 60% | 给两条路：补几个快单 / 提前跟老板对齐预期 |

**给方向，不给判决。** 话说太满会打击士气，而且工具算的是概率，不是命运。

预测准不准取决于数据全不全，所以页面会**直接告诉你漏了几条**：

> 有 5 个在谈商机**没填预计成交日**，这部分只能按最低概率估算——补上日期，预测会准不少。

不藏着掖着，他补上之后预测自然就准了，这是个正循环。

## 商机健康度

每天早上有 10 个在谈商机，真正的问题不是"数据在哪"，而是**"我今天先动哪一个"**。健康度就是回答这个问题的。

### 四个信号

| 信号 | 看什么 | 为什么这条重要 |
|---|---|---|
| **沉默** | 距上次联系多久 vs 这个客户平时的联系间隔 | 客户平时一周一联系、现在三周没动，才是真异常 |
| **停滞** | 在当前阶段停了多久 vs 你历史上这个阶段的典型停留 | 卡在"报价"三个月不动，基本是凉了 |
| **临期** | 预计成交日是不是过了 / 快到了 | 这是**你自己填的承诺**，最有说服力 |
| **无推进** | 近 30 天有没有换过阶段或记过跟进 | 一直"在跟"但从没往前走，等于没跟 |

### 基准是学出来的，不是写死的

这是整个功能最关键的一点。如果全局写死"21 天没跟进就报警"，政企客户（半年周期）会天天飘红——**看几次就麻了，这叫狼来了**。

所以基准分三层，优先级从高到低：

1. **你自己的成交记录**：从已关闭订单的阶段轨迹里，算出每个阶段的停留天数中位数（≥3 个样本才采信）。
2. **这个客户自己的节奏**：他平时的联系间隔中位数 × 1.6。
3. **客户分级的通用值**：只有前面都没有时才用（A/B/C 三档不同）。

用得越久，判断越准。新数据进来会自动重算，不用你管。

### 三个刻意的克制

1. **不误伤**：新建 3 天内的商机不评分（没数据硬算必然误报）；老数据的阶段起点会标"估算"并在文案里说实话。
2. **不监工**：语气是"该盯一盯"不是"警告"；每条提示必须带**一个今天就能做的动作**（且能一键执行）；不满意可以点「知道了」忽略 7 天——**掌控感在销售手里，不在工具手里**。
3. **不依赖 AI**：纯规则计算，断网、没 API Key、刚装上都能用。AI 是增强项，不能是必经路径。

### 校准

「设置 → 商机健康度」可以调整**松紧**（严格 0.7 / 标准 1 / 宽松 1.5）。周期长的生意建议选宽松。首页卡片底部会写明**当前的判断依据**——工具凭什么这么说，不能是黑箱。

> **终态操作要二次确认**：点「要签了」会先弹确认框。赢单/输单直接改写业绩、提成和业绩曲线，一键点错代价太大，中间阶段则不拦。

手机浏览器打开时：

- 适配 iPhone 刘海安全区，支持 PWA 添加到主屏幕

**顶栏 + 页签的高度是实测的，不是写死的。** 这一点单独拿出来说，因为它出过一次真故障：

页签栏是 `position:sticky`，必须贴在顶栏正下方。CSS 里原来写死 `top:55px`（顶栏在桌面上的高度），但手机上顶栏项目会换行，实际是 **187px**——页签往上跑进顶栏里，被 `z-index` 更高的顶栏整条盖住。

后果是：**页面往下一滚，八个页签一个都点不动，滚回顶部又好了。** 这种时好时坏的毛病最难自查。

现在的做法是 JS 用 `ResizeObserver` 实测顶栏高度写进 `--topbar-h`，页签读这个变量；`z-index` 也特意调得比顶栏高，万一哪天同步失灵，宁可页签盖住顶栏底部，也不能让顶栏盖住页签——顶栏被压住只是少一个按钮，页签被压住等于整个应用没法换页面。

回归测试里有一条专门盯它：**先把页面滚到底，再逐个点八个页签**。只在顶部测，这个 bug 永远测不出来。

**为什么用 Blob 而不是 KV**——这是做适配器时最关键的一个决定：

> KV 是**最终一致**的（最长 60 秒陈旧读），而且**没有 CAS**（比较并交换）。
> 同步恰恰是「读 → 合并 → 写」三步。用 KV 会出现：手机读到 60 秒前的旧数据 → 合并 → 写回 → **把电脑刚推上来的记录覆盖掉**。丢的是客户资料和跟进记录，不可接受。
>
> Blob 支持 `consistency: "strong"` 强一致读，也有 `onlyIfNew` 条件写。1GB 免费额度，一个人用根本用不完。

**为什么每台设备写自己的 key**——光有强一致还不够：

> 就算有了强一致读，「读 → 合并 → 写」依然有竞态窗口：两台设备同时读到版本 N，各自合并成 N+1，后写的那个会把前一个的改动盖掉。
>
> 所以不共用一把钥匙——每台设备只写 `sync/<空间>/<设备ID>.json`，读取时把该空间下所有设备的文件全部 `merge` 起来再返回。**读-改-写变成了纯追加，竞态窗口彻底消失。**

## 云同步（连接后端）

### 设计原则：本地优先（Local-first）

这是整个同步方案里最重要的一条，也是我反复权衡后的选择：

> **本地永远是权威数据源，云端只是一个同步通道。**

具体表现为：

- **断网照常能用**。飞机上、地下车库、客户公司信号死角——照样记客户、改阶段、写跟进。联网后自动收敛，不需要你点任何按钮。
- **服务器挂了不影响你干活**。云端故障的表现只是顶栏胶囊变红，本地功能一个不少。
- **随时可导出、随时可撤离**。数据永远在本地有一份完整的、可直接打开的 JSON，不依赖任何厂商。

因此下面这四种做法我明确**不采用**：

| 反模式 | 后果 |
|---|---|
| 数据只放云端 | 断网白屏，销售最需要记录的时刻偏偏用不了 |
| 云端存储但不能一键导出 | 数据被平台绑架，哪天涨价或停服就只能认栽 |
| 全量覆盖式同步（后上传的覆盖先上传的） | 手机上记完，电脑一开把手机的数据冲掉，且不可恢复 |
| 删除不做墓碑 | 电脑上删了客户，手机一同步又给同步回来了，删不掉 |

### 同步机制（三条规则）

1. **整包快照**：每次同步传全量数据。销售数据也就几十 KB，比做增量简单得多，也不容易出诡异 bug。
2. **逐条 LWW**（Last-Write-Wins）：每条记录比 `updatedAt`，谁新留谁。单人顺序操作下 100% 正确；多人同时改同一条，后写的赢。
3. **墓碑软删除**：删除不是真删，而是打 `deleted` 标记并更新 `updatedAt`。这样「删掉了」这个事实才能同步给别人。设置页有「压缩本地墓碑」可以清理。

### 自建后端详解（有自己的机器时选这条）

项目自带零依赖后端 `server.js`，一个文件同时提供**静态网站 + 同步接口**，不需要 npm install，不需要数据库。

```bash
node server.js                      # 默认 8080
PORT=3000 node server.js            # 换端口
SYNC_TOKEN=my-long-secret node server.js   # 专属模式
```

启动后控制台会打印令牌，把它填进每台设备的「设置 → 云同步」：

- 同步方式选「自建 / 兼容服务器」
- 同步地址填 `http://你的IP:8080/api/sync`
- 同步令牌填控制台打印的那个
- 点「保存并连接」，胶囊变绿即成功

**两种运行模式**：

| 模式 | 怎么开 | 行为 |
|---|---|---|
| 专属模式 | 启动时带 `SYNC_TOKEN=xxx` | 只认这一个令牌，其余一律 401。个人自用最省心 |
| 多人模式 | 不带 `SYNC_TOKEN` | 令牌即空间，任意 ≥8 位的令牌都能接入，各占一个数据文件互不干扰。一台服务器全组共用 |

接口一览：

| 接口 | 说明 |
|---|---|
| `GET /api/sync` | 拉取云端快照（云端为空返回 404） |
| `PUT /api/sync` | 推送本地快照，服务端 LWW 合并后返回合并结果 |
| `GET /api/backups` | 列出该令牌的历史版本（需令牌） |
| `GET /api/health` | 健康检查 + 鉴权诊断，不暴露数据 |

**令牌三种携带方式，服务端都认**：`Authorization: Bearer xxx`（标准）、`X-Sync-Token: xxx`、`?token=xxx`。前端两个头都发。

> 为什么要搞三种？实测部分云平台网关（如 CloudStudio Gateway）会**剥掉 `Authorization` 头**，症状是「本地联调一切正常，一上线全部 401」，极难排查。多留两条路就能绕过去。
>
> 排查 401 的正确姿势：打开 `GET /api/health`（带上你的令牌），看返回里的 `authSeen` 和 `authVia`：
>
> | 返回 | 说明 | 怎么办 |
> |---|---|---|
> | `authSeen: false` | 令牌根本没到服务端，被网关吃掉了 | 改用 `X-Sync-Token`（前端已自动双发），仍不行再试 `?token=xxx` |
> | `authSeen: true` 但仍 401 | 令牌到了但不对 | 检查 `SYNC_TOKEN` 环境变量有没有生效 |
> | `mode` 显示"多人模式" | 你以为设了 `SYNC_TOKEN` 其实没生效 | 检查启动命令里的环境变量有没有传进去 |
>
> 补充：`?token=` 这个通道在部分网关上会被网关自己截留（本地和多数反代下正常），所以优先级最低，只作为兜底。

安全与可靠性细节：Bearer Token 鉴权；数据按令牌分文件存储；写入用「写临时文件 + 原子改名」，避免写一半断电损坏文件；请求体 8MB 上限；路径穿越防护；目录不可写时自动退化为内存并打印警告（不会静默丢数据）；端口被占用时给出人话提示而不是甩一段堆栈。

**误同步了怎么办**：这是「最后写入者赢」策略最大的风险——一次误删会同步到所有设备。所以服务端在每次覆盖前自动留档，分两层：

| 层 | 频率 | 保留 | 环境变量 |
|---|---|---|---|
| 近期快照 | 最快 1 分钟一份 | 最近 10 份 | `BACKUP_KEEP`、`BACKUP_MIN_GAP` |
| 每日快照 | 每天一份 | 最近 7 天 | — |

全部可调的环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | 8080 | 监听端口 |
| `SYNC_TOKEN` | 空 | 设了就是专属模式（只认这一个），不设就是多人模式 |
| `BACKUP_KEEP` | 10 | 每个空间保留的近期快照份数 |
| `BACKUP_MIN_GAP` | 60000 | 两份近期快照之间的最小间隔（毫秒） |
| `MAX_SPACES` | 200 | 空间数上限。**公开部署时务必留意**：多人模式下任何人都能建空间，这个上限是防止被刷爆磁盘的护栏 |

误操作后，在 `data/backups/` 里挑一个还完好的版本，复制回 `data/` 并改名为 `store-<那串哈希>.json`，重启服务，各设备重新同步即可回滚。文件名里的哈希就是令牌的 sha256 前 12 位，一个令牌一个文件。

**长期运行**：

```bash
# Docker
docker build -t sales-copilot -f deploy/Dockerfile .
docker run -d --name sales-copilot -p 8080:8080 \
  -e SYNC_TOKEN=你的令牌 -v $(pwd)/sync-data:/app/data \
  --restart unless-stopped sales-copilot

# systemd（见 deploy/sales-copilot.service，含安全加固配置）
sudo systemctl enable --now sales-copilot
```

> **要不要上 HTTPS？** 要，而且这里有个必踩的坑：**如果你的页面是 HTTPS（比如部署在 Vercel / 上面那个在线地址），而同步服务器是 HTTP，浏览器会以"混合内容"直接拦截请求**，表现为同步一直失败且控制台报错。两个办法：
>
> 1. 给同步服务器套一层 HTTPS（推荐）。最省事是用 Caddy，配置文件三行，证书自动续：
>    ```caddyfile
>    sync.yourdomain.com {
>        reverse_proxy 127.0.0.1:8080
>    }
>    ```
>    然后把前端同步地址填成 `https://sync.yourdomain.com/api/sync`。
> 2. 干脆别用在线版，直接让 `server.js` 同时提供页面和接口（`node server.js` 本身就带静态站点），同一个地址同一个协议，没有混合内容问题。
>
> 仅在局域网/本机（http://127.0.0.1 或 http://192.168.x.x）调试时，HTTP 才不受影响。

### 五种方案的取舍

| 方案 | 优点 | 缺点 | 什么时候选 |
|---|---|---|---|
| 不接后端 + 数据码 | 零成本、零依赖、最私密 | 手动 | 只有一个主力设备 |
| 公共演示后端 | 1 分钟就能试 | 安全靠令牌不被猜到、不保证长期存在 | 先验证功能 |
| Supabase 免费版 | 免运维、免费额度用不完、数据在自己账号 | 服务器在境外，国内偶尔卡 | 个人长期用（推荐） |
| 腾讯云 EdgeOne | 有账号就能用、含 CDN 和 HTTPS、适配器已写好 | 数据在厂商 Blob 里、生态较新 | **已经有 EdgeOne 账号（推荐）** |
| 自建 server.js | 数据完全自己掌控、速度最快、可内网部署 | 要一台机器 | 有服务器 / NAS / 团队内部 |
| 腾讯云开发 CloudBase | 国内速度快、和微信生态近 | 有费用、绑定厂商 | 国内团队正式用 |

## 示例数据与「清空」这个动作

这是被真实用户报上来的 bug，值得单独记一笔，因为它的根因不是代码写错，而是**概念本身有歧义**——而且同一句"示例清不掉"，底下藏着**两条独立的路径**，只修一条的话，开同步的用户该复现还是复现。

### 路径一：空库有歧义

**现象**：清空数据、退出网页、再打开——示例数据又回来了，而且一直如此。

**根因**：旧代码判断"要不要灌示例"看的是"客户和商机是不是都为 0"。问题是，**空库有两种完全不同的含义**：

- 新用户第一次打开，什么都没有 → 该给他一套示例看看
- 老用户刚点了清空，他要的就是一个干净的空库 → 给他灌示例，等于把他刚才那一下操作当没发生过

程序分不清这两种空，只能乱猜，猜错了就表现为"怎么清都清不掉"。**空库的歧义，只能靠一个显式的标记来消除。**

于是有了三条铁律，写死在 `store.js` 的 `shouldSeedDemo()` 里：

| # | 条件 | 少了它会怎样 |
|---|---|---|
| 1 | **已完成过引导**标记未置位 | 用户清空过也照样灌，就是本次这个 bug |
| 2 | **本机是全新安装**（localStorage 里压根没数据） | 换设备时会重复灌一遍 |
| 3 | **此刻库里没有任何业务数据** | 老用户换新设备，同步把真实客户拉下来之后，示例照样灌进去，假客户混进真客户里——比重生还难清理 |

三条是**与**的关系，缺一不可。而且第 3 条对**调用时机**有要求：必须在首次同步拉取完成之后再问，拉取之前问等于没问。所以 `ui.js` 的启动顺序是 `load → 渲染界面 → await 首次同步 → 才判示例`，网络不通时这个 await 会 reject，直接吞掉当云端空的处理，不能因为断网就卡住启动。

### 路径二：清空没有传播到云端

路径一修好之后，本地测全绿，真机测也全绿——但**用户是在线上（开着同步）遇到这个 bug 的**。把真服务端接上再跑一遍，示例照样回来了：

```
云端塞入 2 家「历史遗留」的示例客户   [HTTP 200]
同步后本地客户数：10
清空后本地客户数：0
再同步一次后本地客户数：2     ← 回来了
刷新重开后本地客户数：2       ← 还是它
```

根因和路径一完全不同：**清空只在本机生效，云端那条记录还活着**。本地 `state.customers` 直接被清空，一条墓碑都没留，下次同步 `merge(本地空, 云端有)` 时云端那条记录毫无对手，又赢了。

所以 `reset()` 现在会为每条记录生成墓碑再清空：

- 界面上一条不剩（墓碑被 `list()` 过滤掉，用户看到的仍是干净空库）
- 但墓碑会随推送上云，把云端的旧记录一并标记删除
- 别的设备拉取后也会跟着清掉——**「清空」终于变成了一个能传播的动作**
- 墓碑由设置里的「压缩数据」（`purge`）清理，不会一直膨胀

### 示例数据永不上云（但墓碑必须放行）

光判定对还不够。还有一条路径能把示例塞进云端：

> 新设备打开 → 还没配同步 → 自动灌了示例 → 之后配上同步 → 一把推上去

于是给示例数据打了 `demo` 标记，云同步推送时过滤掉。规则只有一句话：**你改过的就是你的**——用户在某条示例上动了一个字（改客户名、改金额、写跟进），`update()` 就摘掉标记，它转正成真实数据，正常参与同步；没动过的示例连删除墓碑都不往云端发（云端从来没有过这条，不需要为它留墓碑）。

这里踩过一个坑：**不能**在 `snapshot()` 里过滤。`snapshot()` 还有一个用途是给 `applySnapshot()` 提供"本地这一侧"去和远端合并，在那儿过滤掉示例，合并结果里就没有示例，写回 state 时本地刚灌的示例会被当场抹掉——用户一同步示例就没了。所以推送载荷单独拆了个 `pushPayload()`。**推送（往外发）和合并（跟自己比）是两件事。**

过滤条件最后写成 `!r.demo || r.deleted`——**示例的墓碑要放行**。因为云端可能还留着历史上推上去的示例客户（那时候示例没打标记），墓碑是唯一能清掉它们的东西；连墓碑一起过滤，那批旧示例就永远删不干净了。

### 顺带挖出来的第三个 bug：清空会静默断掉云同步

排查路径二的时候，诊断打出来的是"云端有 c1、c2，本地却完全空"——同步压根没执行。查下去发现：`reset()` 和 `seed()` 都会 `state = emptyState()`，把 `settings.sync`（endpoint + token）一起清掉，`mode` 悄悄变回 `off`。

这个 bug 比前两个都阴：

- 界面**一声不吭**，同步胶囊不动、不报错、不提示
- 用户以为数据还在往云端传，实际上早就断了
- 等他在另一台设备上发现数据对不上，可能是几周以后的事
- 而清空对话框写的是"删除客户、商机、跟进记录（话术库保留）"，压根没提同步

修法是一句话的原则：**配置和数据是两回事，数据可以清空，配置不能。** 现在 `reset()` / `seed()` 都整份保留 `settings`（owner、目标金额、AI 配置、云同步、已引导标记），只换业务数据。

**技术选择说明**：原生 HTML/CSS/JS，零依赖、零构建、零 npm install。图表全部手写 SVG，不引 CDN，断网照常显示。所有文件用传统 `<script src>` 而非 ES Module，确保 `file://` 双击打开也能跑。后端同样零依赖，只用 Node 内置模块。

**`sync-core.js` 是「合并算法」的唯一源头。** `server.js` 直接 `require` 它；EdgeOne 的函数是 ESM 环境、又不能跨目录 `require`，所以由 `prepare.js` 把 `SYNC-CORE-BEGIN/END` 标记之间的逻辑体提取出来生成一份 ESM 副本。

为什么不让两端各写一份：合并算法是最不能出错也最容易悄悄漂移的地方。两份实现只要有一次改动没同步，就会出现「本地同步正常、线上丢数据」这种诡异现象。标记提取 + 测试比对，让漂移在构建阶段就暴露。

## AI Agent 时代，这个项目还要怎么打磨

从一个干了多年销售、现在开始用 AI 的业务员视角看，现在的版本只是**把 Excel 和脑子里的信息结构化**，下一步真正值钱的是**让 AI 替我读数据、出主意、动手**。路线图我分成四个阶段：

### 阶段 1：已经做了——数据结构化 + 移动端顺手
销售日常工作就是三个动作：记、看、打。把客户、商机、跟进放到一个页面上，手机上能一键拨号，已经是把效率从 70 分拉到 90 分。很多 CRM 连这点都没做好。

### 阶段 2：AI 当秘书——已基本实现
让 AI 读我的数据，帮我写周报、写跟进话术、复盘输单。这一步的关键不是技术，而是**Prompt 工程**：怎么把客户画像、最近跟进、商机阶段喂给 AI，让它输出的不是废话，而是能直接复制粘贴的话术。

这一阶段后来又补了三块，都遵循同一个原则——**能用规则算的就不花钱调模型**：

| 能力 | 怎么做 | 为什么 |
|---|---|---|
| **周报** | 纯本地统计，AI 只做最后一步润色 | 销售写周报的痛苦不是不会写，是**想不起来这周干了什么**。归拢动作要的是**确定**，AI 会漏掉一条跟进，算术不会 |
| **聊天记录情报提取** | 本地规则拆四桶（顾虑/承诺/决策/下一步） | 拆结构是模式匹配，不是创作。断网也要能用 |
| **战后沉淀** | 本地从跟进历史挑候选话术，人勾选 | 挑出来的是**自己说过的话**，不是 AI 编的 |

### 阶段 2.5：看过一个同款项目之后的取舍

有个用 Next.js 14 + Supabase + pgvector 做的同款（1 万条共享知识库、向量检索、联网搜索、多模型适配器）。**它的架构我一条都没抄，但有三件事我照着做了**：

| 它做的 | 我怎么落地 | 理由 |
|---|---|---|
| 混合检索（向量 0.5 + 关键词 0.5） | **本地四路加权**（意图 0.40 + IDF bigram 0.30 + 全文 0.15 + 标签 0.15） | 「混合」这个思路是对的，但**不一定要用向量**。个人话术库撑死几百条，IDF + 意图词表已经够准，还不用 embedding、不用联网、双击就能用 |
| 从对话里提取结构化情报 | 聊天记录拆四桶，勾选后一键写入跟进 | 这条完全同意，直接抄了思路 |
| 自动生成周报 | 本地算初稿 + AI 润色 | 同意它做这件事，**不同意它交给模型做全部**。数字必须来自本地账本 |
| 沉淀话术 | 赢单/输单时自动从跟进历史挑候选 | 它没做，但和上面两条是一回事，补上了 |

**明确不跟的四条**：

1. **pgvector + 1 万条共享知识库** —— 对个人销售是负担而不是资产。要 Supabase、要 embedding API 花钱、要联网。更要紧的是：**销售最值钱的知识是自己客户说过的话，不是通用话术库**。1 万条别人的话术，不如 50 条自己踩过的坑。
2. **联网搜索（Tavily 那类）** —— 个人销售场景用不上，国内访问不稳定，还要再付一份钱。真要查客户公司背景，销售自己搜比我接 API 准。
3. **向量数据库作为必选依赖** —— 一旦向量库挂了或者 Key 过期，检索就全废。本地检索**没有这个失效模式**。
4. **共享知识库** —— 引入它就要处理「谁的知识」「能不能信」，个人工具不该有这些问题。

一句话总结这次借鉴：**学它的产品思路，不学它的技术选型。** 它是"团队 + 云 + AI 全家桶"的路子，我是"一个人 + 断网能用 + 本地优先"的路子。两者都对，只是服务对象不同。

### 阶段 3：AI 当军师——四条已做三条，剩下的不是技术问题

- ✅ **自动识别"假性商机"**：已实现，见上节「商机健康度」。**刻意用规则而非 AI 实现**——断网能用、不花钱、结果可解释，而且不会因为模型抽风给出莫名其妙的判断。
- ✅ **预测本月回款**：已实现，见上节。给**保守/乐观区间**而不是一个假精确的数字，并附上目标倒推（"这个月还来得及吗"）。同样用规则实现。
- ✅ **每日晨报**：已实现。第一屏只回答三件事——今天有几件事、最紧急的是哪件、这个月还行不行。刻意做成**导航而非又一张列表**，详情交给下方卡片。
  - 排序上踩过一个坑：最初按逾期天数排，结果"逾期 25 天的 C 级小单"压过了"刚逾期 1 天的 A 级大单"。但销售的真实判断是——**刚逾期最该补，拖过一个月的基本已经凉了**。改成非线性打分（等级 + 逾期分段 + 在谈金额）后才对。
- ⬜ **客户情绪/关系热度打分**：**我倾向于不做**。规则做不准（"客户回复积极"怎么量化？），AI 做要花钱且不稳定，而且很难比得上销售自己的直觉——你打完一通电话就知道这单有没有戏，这个判断不该交给算法。做了反而可能误导。

**这一阶段值得记一笔的发现**：原本以为要靠 AI 的三件事，有三件用规则做得更好。理由不是技术，是**场景**——

销售在电梯口、地铁里、客户公司楼下用这个工具。这些地方没网、没时间、没耐心等模型返回。而"这个单子是不是凉了""这个月还差多少"这类判断，本质是**对已有数据的统计推断**，规则不但够用，而且**可解释**：工具得能说清"我为什么这么判断"，否则销售看两次就不信了。

AI 真正该上的地方，是**生成**而不是**判断**——写话术、写周报、把一句口语拆成结构化字段。这也是「AI 助手」页在做的事。

### 阶段 4：AI 当队友——后端已就绪，权限仍是空白
- **自动抓取外部信息**：输入客户公司名，自动查官网/工商/新闻，生成"客户情报摘要"
- **语音录入跟进**：说完一句话，AI 自动分字段填入客户/商机/跟进记录
- **团队共享客户池**：同步后端已经铺好路，但现在的合并策略是 LWW，**没有权限、没有归属隔离**——多人共用会互相覆盖，只适合"一个人多设备"或"大家各填各的空间名"
- **AI 陪练**：输入客户常见拒绝理由，AI 扮演客户让我练话术

**我的判断**：对一线销售来说，阶段 1 和 2 是雪中送炭，阶段 3 开始锦上添花，阶段 4 才是公司级项目。现在先守住"个人作战台"这个定位，别急着做成第二个 CRM。

要真做多人协同，缺的不是技术，是三件麻烦事：**归属权**（这条客户是谁的）、**可见性**（谁能看谁）、**冲突的现实语义**（两个人同时改金额，LWW 会让一方的修改凭空消失，这在团队里是要吵架的）。到那一步就该换数据库 + 账号体系了，而不是继续在 JSON 快照上打补丁。

同步测试同时跑本地和线上两套环境，是因为**本地过了不等于线上能过**——这次就靠线上这一遍抓到了网关剥 `Authorization` 头的问题，而本地怎么测都测不出来。

同步联调里最值得单独说的是这三条，它们是最容易做错的地方：

- **删除不复活**：A 删了客户，B 同步后消失；再让 B 反复推送，A 也不会把这条数据"复活"。靠的是墓碑 + `updatedAt`。
- **断网可用**：把设备 A 切成 offline，照样能开弹窗、记客户；同步失败只让胶囊变红，本地数据一条不少；恢复网络后离线新增的数据自动补传到 B。
- **失败不伤数据**：令牌填错时同步报 401，本地 11 家客户完好无损；改回正确令牌立刻恢复。

健康度的测试里有一条值得单独说，因为它暴露的不是 bug 而是**测试本身的盲区**：

测试最初断言"点「推进一步」后阶段确实变了"，通过了。但看输出才发现，被推进的是 `negotiate → won`——**点一下按钮就把 26.8 万的单子标成了赢单，还弹了庆祝动画**。这会直接污染业绩、提成和业绩曲线。测试断言只检查了"变了"，没检查"变得对不对"。现在终态（赢单/输单）一律二次确认，测试也相应加了"终态按钮不得直接改数据"的断言。

**凡是会改写业绩数字的操作，都不能一键完成。** 这条后来写进了实现原则。

### 三条测试原则（都是吃过亏之后定的）

1. **不能只验证「渲染出来了」，必须验证「点得动」。** 用 `elementFromPoint` 做命中测试，而不是看 DOM 里有没有这个节点。这次就是这么抓到「页面一滚动，八个页签全被顶栏盖住」的。
2. **不能只验证「变了」，必须验证「变得对不对」。** 上面那条「推进一步把单子推进赢单」就是教训。
3. **测试本身也要被验证。** 加了「滚动后点页签」这条之后，我反过来把旧的 bug 注入回去（`.tabs{top:55px;z-index:29}`），确认测试真的会失败——**8/8 个页签全部报「点不动」**。不加这一步，所谓「测试通过」可能只是测试写错了，永远返回绿。

还有两个**排查方向**比结论更值钱，记在这里：

- **命中测试报「被遮挡」，先怀疑测试。** 一次扫描报「复制按钮被弹窗标题栏遮挡」，但真点却成功了。原因是命中测试没先滚动，按钮在视口之外，测的那个坐标上碰巧躺着标题栏。真实用户不会去点一个看不见的按钮——他会先滚过去。**Playwright 的 click 自带滚动，所以「真点能过而命中测试报错」这个矛盾本身就是线索。**
- **换行长链接的中心点是个陷阱。** 一个 84px 宽、换行成两行的商机链接，中心点落在两行之间的缝隙上，`elementFromPoint` 返回父容器 TD——但左上、左中、首行文字三个点全部命中自身。用户点的是**看得见的文字**，不是矩形的几何中心。只测中心点，等于给所有换行链接批量制造假警报；假警报一多，真遮挡就被淹没了。

### 这一轮修掉的六个真 bug

| bug | 后果 | 怎么发现的 |
|---|---|---|
| 页签 `top` 写死 55px，手机顶栏 187px | 页面一滚，八个页签全点不动 | 手机端滚动后逐页签点击 |
| 战后沉淀读 `x.note`，实际字段叫 `content` | 功能从来没生效过，且不报错 | 测试第一条断言「它必须能吐出东西」 |
| `tags` 可能是数组也可能是字符串 | 用户自建一条带关键词的话术后，搜索直接崩 | 类型冲突回归测试 |
| `build.js` 脚本清单硬编码 | 单文件版一直缺三个模块，话术库和周报是坏的 | 改为从 HTML 解析脚本清单 |
| toast 的 `pointer-events:auto` | 弹提示的 2.4 秒里压住底部按钮 | **特意在 toast 还挂着时扫描** |
| ESM 里 `new Response('', {status:204})` | 204 不允许带 body，预检全 500，线上跨域同步彻底失效 | 适配器测试 |

最后一条值得单独说：204 那个 bug 只在**线上**才会暴露，本地怎么点都点不出来——又一次印证了「本地过了 ≠ 线上能过」。

## 已知边界

- **同步是"一个人多台设备"的设计**，不做权限、不做归属隔离。多人共用同一个空间会互相覆盖（最后写的赢），要分开用就各填各的空间名 / 令牌。
- **LWW 的代价**：同一条记录在两台设备上**离线**分别修改再联网，先写的那次改动会被静默丢弃，没有冲突提示。个人使用几乎遇不到，团队使用不可接受。
- **墓碑会占空间**：删除是软删除，本地会留 `deleted` 标记。数据量大时可在设置页「压缩本地墓碑」清理，清理后该条删除记录不再向新设备传播（已同步过的设备不受影响）。
- **公网部署请上 HTTPS**：HTTP 环境下令牌和客户手机号是明文传输的。
- 无痕模式 / 某些受限环境无法写 localStorage，顶栏会在「设置」里提示不可持久化，此时请及时导出数据码或 JSON 备份。
- 示例数据是虚构的（恒力精工、优鲜到家等），用来演示图表效果，正式使用前请「设置 → 清空全部业务数据」。
- **周报、话术检索、情报提取、战后沉淀全部是本地规则实现**，不是 AI。好处是断网可用、不花钱、结果可解释；代价是**不能理解语义**——「客户说预算砍半」和「客户说没钱了」在规则眼里是两句话，AI 知道是一回事。需要语义理解时用「AI 助手」页或周报的「AI 润色」按钮。
- **周报的「本周」从周一起算**。如果你的公司按别的口径统计，数字会和你手里的表格对不上。
- **EdgeOne 方案的两个限制**：① 数据在厂商 Blob 里，长期归档靠前端 JSON 备份；② 每个空间默认最多 20 台设备（`MAX_DEVICES` 可调），超了就不再接受新设备的写入——**换手机换电脑多了记得清理旧设备文件**。
- **单文件版是构建产物**，改完任何 js/css 都要 `node build.js` 重新生成，否则你双击打开的那份还是旧的。
